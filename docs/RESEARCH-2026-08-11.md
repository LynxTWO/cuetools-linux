# Cross-platform .NET GUI frameworks for a WPF-to-Linux port (2026)

## 1. Avalonia UI — the front-runner

**WPF-port effort: Low (lowest of any option).** Avalonia is deliberately WPF-shaped: same layout system (Grid/StackPanel/DockPanel behave identically), same binding/MVVM model, XAML that "feels familiar within ten minutes." Differences: `.axaml` extension, different xmlns, CSS-like style selectors instead of Triggers (no `DataTrigger` — use style classes/pseudoclasses or behaviors), explicit `Program.Main` startup. Avalonia's own porting guide says typical WPF ports run "weeks, not quarters." (There is also **Avalonia XPF**, a commercial near-drop-in WPF compatibility layer, if you want an almost zero-change port — but it is paid and heavier.)

**Visual ceiling: High — equal to or better than stock WPF.** Everything is custom-drawn via Skia, so it looks *identical* on Ubuntu and Windows. Ships with a Windows-11-style **Fluent 2 theme** covering every built-in control; strong third-party themes: **FluentAvalonia** (WinUI controls/fluent design), **SukiUI**, **Semi.Avalonia**, **ShadUI** (shadcn-inspired), Material.Avalonia. Avalonia 12 added themeable client-side window decorations (custom title bars that still respect platform conventions).

**Trimming/NativeAOT + real sizes (linux-x64, self-contained):**
- Default `PublishTrimmed=true`: minimal app ~**58 MB** unzipped (25 MB zipped); single-file trimmed ~**50.8 MB**; with `TrimMode=link` ~**37.4 MB** (16.1 MB zipped) — from the official size-trim discussion (#9217). One real app's installer went 45 MB → **15 MB** with trimming+single-file+link mode.
- **NativeAOT** (fully supported, documented): community templates report ~**18 MB** single-file with UPX (lixinyang123/AvaloniaAOT; ~13 MB NSIS installer) and ~**15 MB** with UPX (peaceshi/Avalonia-NativeAOT-SingleFile). Uncompressed NativeAOT single-file realistically lands ~**25–40 MB** on linux-x64.
- Real-world 2026 data point: **UniGetUI v2026.2.3** (Avalonia) switched to NativeAOT — installer 58.0 → **28.3 MB**, portable zip 85.6 → **39.5 MB**, Linux .debs roughly halved.
- Extra savings: `InvariantGlobalization=true` drops ICU (~30 MB), set `SatelliteResourceLanguages`, single `RuntimeIdentifier` strips other OS backends.

**Linux packaging:** first-class. Official docs for **.deb** (runtime deps just `libx11-6, libice6, libsm6, libfontconfig1`), plus AppImage, RPM and **Flatpak** (declare `xdg-desktop-portal` for file pickers). The team's **Parcel** tool automates .deb/.rpm/.zip with desktop-file integration.

**Maturity (2026): Excellent.** **Avalonia 12 shipped April 7, 2026** (targets .NET 10 + SkiaSharp 3): 4x faster startup with NativeAOT (1,960 ms → 460 ms on Android), up to 1,867% FPS gains in heavy scenes, open-sourced WebView (no Chromium bundling), and it is *the first .NET UI framework with a native Linux accessibility backend* (AT-SPI2). Very active commercial + OSS development.

## 2. Uno Platform

**Port effort: Medium-high.** Uno speaks the **WinUI 3 XAML dialect**, not WPF — you'd translate WPF XAML to WinUI idioms (different control set, `x:Bind`, VisualStateManager-centric). Worth it mainly if you also want Web (WASM) + mobile from one codebase.

**Visual ceiling: High.** Skia-rendered Fluent/WinUI styles plus Material; on Linux it renders via Skia to **X11** (or framebuffer for embedded); the old Skia+GTK head is legacy. Pixel-identical cross-platform like Avalonia.

**Sizes: the heaviest here.** A *blank* self-contained desktop app was ~**200 MB**, cut 74% to ~**52 MB** with full IL trimming + XAML/resource trimming (Uno 5.6 era, .NET 9). Expect roughly similar on Linux — ~2–3x Avalonia's footprint. NativeAOT support on desktop is newer/less proven than Avalonia's.

**Packaging:** standard `dotnet publish` output; snap/deb/AppImage/flatpak all doable but more DIY than Avalonia's tooling.

**Maturity:** Very active (Uno 6.x through 2026, Uno Platform Studio/Hot Design); large surface area, heavier framework, some tooling behind paid tiers (free for small companies/OSS).

## 3. Gtk# / Gir.Core

**Port effort: Very high — a full UI rewrite.** No XAML; you build GTK4 widget trees in C#. GtkSharp covers GTK3 only; **Gir.Core** is the GTK4/libadwaita path — currently **v0.8.x, pre-1.0, API explicitly unstable**, though actively maintained (tracks GNOME 48 / GTK 4.18 / libadwaita 1.7).

**Visual ceiling: Native GNOME/libadwaita polish** — looks perfectly at home on Ubuntu/GNOME, but you're constrained to the Adwaita design language; it will not look like your WPF app, and rich custom visuals are much harder than in XAML.

**Size: the smallest possible.** GTK4 is a *system library* on Ubuntu, so you ship only your code + bindings: a trimmed/NativeAOT app can be **well under 10 MB**, and framework-dependent builds are ~1–3 MB. Flatpak with the GNOME runtime is the ideal channel; .deb works naturally (depends on system GTK4); AppImage is awkward (bundling GTK is painful).

**Maturity:** Active but pre-1.0; small community; expect breaking changes.

## 4. Photino (webview-based)

**Port effort: Very high — UI rewritten in HTML/CSS/JS** (or Blazor via Photino.Blazor, which at least reuses your C#). 

**Visual ceiling: Unlimited** (it's the web), but rendering depends on the *system* **WebKitGTK** on Linux — real version-fragmentation pain (project historically tied to `libwebkit2gtk-4.0-37`; flatpak + .NET 8 needs 4.1), and WebKitGTK ≠ Chrome for CSS fidelity.

**Size:** The Photino native library is **< 1 MB** — marketing says "up to 110x smaller than Electron" because the webview is the OS's. But a *self-contained* .NET app still bundles the runtime: realistically ~**20–30 MB trimmed**; framework-dependent builds are a few MB but require .NET installed. NativeAOT is not a well-trodden path here.

**Maturity:** Photino.NET 4.0.x on NuGet, maintained but small community and slow cadence; least corporate backing of the polished options.

## 5. Eto.Forms

**Port effort: High.** Different, smaller widget API (limited XAML via Eto.Serialization.Xaml); maps to *native* toolkits — WPF on Windows, **GTK on Linux**.

**Visual ceiling: Low** — lowest-common-denominator native controls; fine for utilitarian tools, nowhere near WPF's custom-drawn richness. 

**Size:** Small-ish on Linux since GTK comes from the system; the bundled .NET runtime dominates (~30 MB trimmed self-contained).

**Maturity:** Alive — packages updated as recently as **March 2026** (2.11.0) — but essentially a one-maintainer project with a small ecosystem.

---

## Recommendation: "as pretty as WPF, smallest realistic size"

**Avalonia (11.3/12) is the clear winner** — it is the only option that simultaneously (a) reuses most of your WPF XAML/MVVM skills and much of the markup, (b) matches or beats WPF's visual polish on Ubuntu via Fluent 2 / FluentAvalonia / SukiUI with pixel-identical Skia rendering, and (c) gets genuinely small:

- Publish: `dotnet publish -r linux-x64 -c Release -p:PublishAot=true -p:StripSymbols=true -p:InvariantGlobalization=true` (single-file) → expect ~**25–40 MB** uncompressed for a real app, ~**15–18 MB** with UPX; a **.deb/AppImage in the 15–30 MB range is realistic** (UniGetUI's Avalonia NativeAOT build ships a 28 MB installer for a substantial app).
- If NativeAOT trips on a dependency, fall back to self-contained + `PublishTrimmed` + `TrimMode=link` → ~**37–50 MB** unpacked, ~16–22 MB compressed.
- Package as **.deb** for Ubuntu (smallest, 4 tiny system deps) and optionally **AppImage** for portability; Flatpak only if you want store distribution (its runtime download dwarfs your app anyway).

Runners-up by criterion: absolute smallest binary = **Gir.Core/GTK4** (sub-10 MB) but demands a full rewrite and locks you into the Adwaita look; Uno only if WebAssembly/mobile targets matter (pay ~2x size); Photino only if you'd rather build the UI as a web app; Eto.Forms only for plain utility UIs.

# CUETools on Linux — state as of August 2026

## (1) Native Linux version of the CUETools GUI

- **Upstream CUETools (gchudov/cuetools.net) remains Windows-only.** Latest official release is **v2.2.6 (2024-06-28)**; requirements are .NET Framework 4.7 + MSVC redistributable, and no release since 2.1.9 (2021) mentions Linux/Mono/cross-platform. The repo is still actively maintained (last push **2026-08-08**, merging PR #402 "Use HTTPS for AccurateRip database lookups"; other 2025 work: libFLAC 1.4.3→1.5.0, FFmpeg.AutoGen 6.1→7.1.1, C2-error-mode drive fixes).
- **There is a working native Linux build — but of CUERipper, not the full CUETools converter GUI.** Fork `UnknownException/cuetools.net` (author Max Visser, branch `cueripper-avalonia`) rewrote the CUERipper UI in **Avalonia 11.2.1** targeting **.NET 8** (`net8.0`, self-contained `linux-x64` publish; on Linux the csproj builds net8.0 only). Releases run **v2.2.6 → v2.2.6g (2025-08-02)** and ship a `CUERipper.Linux64_2.2.6g.tar.gz` artifact. The `publish_linux64.sh` script compiles native `libFLAC.so` and `libmp3lame.so` (LAME 3.100) and publishes the netstandard2.0 codec plugins for Linux. Release notes describe it as "**Minimal native Linux support – Early compatibility for Linux users (no automated builds yet)**"; features include album-cover selector, multi-encoding, automatic ripping, **CTDB repair functionality ("same as in CUETools")**, in-app updater, dark/light theming. Reported running on LMDE 7.
- This work is **draft PR #372** against upstream (opened 2025-03-09, still open/unmerged as of mid-2026; upstream maintainer c72578 called it "impressive" but no architectural decision to merge yet). The full CUETools batch converter/verifier GUI itself has **no native Linux build** — the fork's `CUETools_2.2.6g.zip` is still the Windows app.
- Context from upstream issue #60 ("Build for Linux?", open since 2020-07-27): a Dec 2023 comment lays out why a port is non-trivial (parts still .NET Framework 2, native codec DLLs, Windows-only UI stack — would need MAUI/Avalonia rewrite).

## (2) Wine and Mono

- **Wine: yes, works reasonably well.** A detailed guide (blobfolio.com, 2023-07-05) runs CUETools 2.2.4 under Wine with winetricks `dotnet48` + `vcrun2019`. Verification and **CTDB repair work**, WAV output works; caveats: window-resize glitches, crash if a remembered cue path no longer exists, and external encoder plugins are unreliable — the author recommends doing lossy/lossless transcoding with native Linux tools instead. The HA wiki similarly documents Wine (via winetricks/PlayOnLinux with .NET Framework + VC2008 runtime) as a supported path.
- **Mono: partially.** The Hydrogenaudio wiki states CUETools runs under Mono **with only WAV audio supported** (the optimized codecs are native Windows DLLs / not ported). A comment on issue #60 (2024-08-28) confirms `mono CUETools.exe` runs, but **building still requires Windows**. So Mono is usable for cue-sheet manipulation and verification logic but not for real FLAC/APE/TTA/WavPack transcoding.

## (3) Linux-native alternatives and remaining gaps

**Ripping + AccurateRip verification (at rip time):**
- **whipper** (whipper-team/whipper): Python 3 ripper, AccurateRip **v1+v2** verification, MusicBrainz metadata. Last release **v0.10.0 (2021-05-17)** — no release in 5+ years, though the repo is not dead (last push 2026-02-17; 175 open issues). **No CTDB support.**
- **cyanrip** (cyanreg/cyanrip): C ripper using cd-paranoia + FFmpeg. Last release **v0.9.3.1 (2024-06-05)**, repo active (pushed 2026-08-04). Verifies **EAC CRC32 + AccurateRip V1/V2**, full pregap handling, HDCD decode, deemphasis, ReplayGain v2, parallel multi-format encode (flac/opus/mp3/tta/wavpack/alac/vorbis/aac), auto offset finding. Packaged in Debian, Alpine, Arch (AUR), openSUSE, Void, NixOS, FreeBSD. **No CTDB support.**

**AccurateRip verification of existing rips (CUETools' verify job):**
- **ARver** (arcctgx/ARver): Python tool that fetches AccurateRip checksums and verifies already-ripped files; **v1.5.0 (2025-11-11)**, active (pushed 2026-06-28), on PyPI.
- Older/niche: spadev/cdrip-tools (`arverify.py`, AR v1+v2 + offset detection), leo-bogert/accuraterip-checksum, ARCue.pl.

**CTDB verification/repair (CUETools' most unique job):**
- **ctdb-cli** (Masterisk-F/ctdb-cli): new in 2026 — a **Linux command-line frontend to the actual CUETools.net CTDB code**, running on **.NET 10** (created 2026-01-18; latest **v2.2.6_0.5.0, 2026-05-09**). Does CTDB parity calculation from CUE+WAV/FLAC (multi-file CUE supported), **verification, repair, and submission** to CTDB, with CUE encoding auto-detection and XML output. Builds CUETools 2.2.6 libraries with patches via configure/make + `dotnet publish`. Very young (2 stars) but it is the first native-Linux CTDB verify/repair path outside Wine.

**Cue sheet processing / transcoding:**
- The shell **`cuetools` package** (svend/cuetools: `cuebreakpoints`, `cueconvert`, `cueprint`, `cuetag`) is essentially dormant: upstream **1.4.1** dates to 2013 (Debian ships 1.4.1-0.2 unchanged from bullseye through trixie/sid; repo last pushed 2023-12-31). Combined with `shntool` and `flac` it covers splitting/tagging but not CUETools' full "album image" fidelity (every cue style, pregap/HTOA preservation, embedded cue, RAR input).
- **flac 1.5.0** (libFLAC 1.5.0, 2025-02-11) added multithreaded encoding, narrowing CUETools' historical speed advantage from its optimized encoders (FLACCL etc.).

**Remaining gaps vs CUETools on Linux:** no native GUI for batch convert/verify of existing rips; no single tool combining AccurateRip + CTDB verify + repair + cue-style conversion; CTDB support absent from both major native rippers (whipper, cyanrip); CUETools' lossyWAV/APE/TTA encoder stack and its EAC-style log ecosystem have no direct native equivalent. Wine (or the CUERipper-Avalonia fork + ctdb-cli) is still required to fully replicate the CUETools verify/repair workflow.

## (4) Community porting efforts

- **UnknownException/cuetools.net `cueripper-avalonia`** — the flagship effort (details above): draft **PR #372** (2025-03-09 → still updated through July 2026), releases to **2.2.6g** with Linux64 tarballs; not yet merged upstream.
- **Masterisk-F/ctdb-cli** (Jan–May 2026) — ports the CTDB client portion of the CUETools codebase to .NET 10 on Linux (SDK-style csproj conversion, TagLib# fixes).
- Upstream issues **#60 "Build for Linux?"** (open since 2020) and **#312 "Docker"** (2024) show ongoing demand; upstream has ~64 forks but no other substantive Linux port surfaced in searches.
- Hydrogenaudio has long-running threads on running CUERipper/CUETools on Linux (e.g. topic 98157 "Running CUERipper on Linux"; HA returns 403 to automated fetches, so thread contents were only sampled via search snippets).

# CUETools (gchudov/cuetools.net, master ≈ v2.2.6) — portability architecture

## 1) Target frameworks of the core libraries (all SDK-style `Microsoft.NET.Sdk` csproj, multi-targeted)

| Project file | TargetFrameworks |
|---|---|
| `CUETools.Codecs/CUETools.Codecs.csproj` | `net20;net47;netstandard2.0` |
| `CUETools.CDImage/CUETools.CDImage.csproj` | `net20;net47;netstandard2.0` |
| `CUETools.AccurateRip/CUETools.AccurateRip.csproj` | `net20;net47;netstandard2.0` (refs CDImage, Codecs, Parity) |
| `CUETools.CTDB/CUETools.CTDB.csproj` | `net20;net47;netstandard2.0` (net20 branch refs `System.Management`; net47/netstandard use the `DeviceId` 4.0.0 NuGet package) |
| `CUETools.Processor/CUETools.Processor.csproj` | `net47;netstandard2.0` (refs AccurateRip, CDImage, Codecs, Compression, CTDB, Ripper, Freedb, TaglibSharp, Newtonsoft.Json 13.0.3 — **no** WinForms/WPF refs) |
| `CUETools.Ripper/CUETools.Ripper.csproj` | `net47;net20;netstandard2.0` (the ripper *abstraction*: `ICDRipper : IAudioSource, IDisposable` defined in `CUETools.Ripper/Ripper.cs`, plus `CDDrivesList.DrivesAvailable()`) |
| `CUETools.Codecs.Flake/CUETools.Codecs.Flake.csproj` | `net47;net20;netstandard2.0` — pure-C# FLAC encode/decode |
| `CUETools.Codecs.ffmpeg/…csproj` | `net47;netstandard2.0`, uses FFmpeg.AutoGen 7.1.1 (portable P/Invoke bindings) |

CLI front-ends are explicitly cross-platform-targeted: `CUETools.ARCUE/CUETools.ARCUE.csproj` (former ArCueDotNet) and `CUETools.Converter/CUETools.Converter.csproj` both target **`net47;netcoreapp2.0`**, OutputType `Exe`. So the maintained core is netstandard2.0 + netcoreapp console hosts; nothing in the core stack is net-only-2.0 legacy.

## 2) Hard Windows dependencies and why

- **GUIs (old-style, non-SDK csproj, net47, `WinExe`)**: `CUETools/CUETools.csproj` (WinForms — `System.Windows.Forms`, `frmCUETools.Designer.cs`), `CUERipper/CUERipper.csproj` (WinForms), `CUERipper.WPF/CUERipper.WPF.csproj` (WPF — PresentationCore/Framework/WindowsBase, WPF ProjectTypeGuid `{60dc8134-…}`), plus `CUEPlayer`, `CUEControls`.
- **CD drive access**: `CUETools.Ripper.SCSI/CUETools.Ripper.SCSI.csproj` (`net47;net20` only — deliberately *not* netstandard) implements `ICDRipper` on top of `Bwg.Scsi` + `Bwg.Logging`/`Bwg.Hardware`. `Bwg.Scsi/WinDev.cs` P/Invokes **`CreateFile`, `DeviceIoControl`, `CloseHandle`, `FormatMessage`** — i.e. Win32 SPTI (SCSI passthrough) against `\\.\X:` device handles; `Device.cs`/`Command.cs` build raw MMC commands sent through DeviceIoControl.
- **Native/x86-x64 codec plugins**: solution is built as Any CPU + **x64 + Win32** by `.github/workflows/CI-windows.yml` (windows-2022 runner, VS2022 devenv, no Linux job). ThirdParty submodules are patched and compiled natively: FLAC, WavPack, MAC SDK (Monkey's Audio, unpacked from zip), taglib-sharp, WindowsMediaLib. P/Invoke wrapper projects for those Windows DLLs: `CUETools.Codecs.libFLAC` (`FLACDLL.cs`), `CUETools.Codecs.libmp3lame`, `CUETools.Codecs.libwavpack`, `CUETools.Codecs.MACLib`, `CUETools.Codecs.TTA` (ttalib-1.1), plus one true C++ project `CUETools.AVX/CUETools.AVX.vcxproj` (SIMD kernels). Platform-API-bound codecs: `CUETools.Codecs.WMA` (Windows Media Format SDK), `CUETools.Codecs.CoreAudio` (Apple CoreAudioToolbox.dll for AAC/ALAC on Windows), `CUETools.Codecs.DirectSound` (playback). `CUETools.CTDB.EACPlugin` (+ `.vdproj` installer) is a plugin for Exact Audio Copy, Windows by definition. `CUETools.Codecs.FLACCL`/`CUETools.CLParity` need OpenCL (portable in principle, shipped for Windows).

## 3) What Linux CD-drive access would need

The clean seam already exists: `ICDRipper` (netstandard2.0, `CUETools.Ripper`) is what `CUERipper`/`CUETools.Processor` consume; only `CUETools.Ripper.SCSI`+`Bwg.Scsi` are Windows. A Linux backend would replace `WinDev.cs`'s CreateFile/DeviceIoControl with the **`SG_IO` ioctl** on `/dev/sr*` (open(2) + ioctl(2) via P/Invoke of libc, `struct sg_io_hdr`), issuing the same MMC `READ CD (0xBE)` commands with C2 error pointers and subchannel data that the existing code builds — CUERipper's own multi-pass re-read/C2 logic in `CUETools.Ripper.SCSI/CDDriveReader` would port almost unchanged on top of it. Alternatives: **libcdio** (wraps SG_IO/cdrom ioctls, gives drive enumeration to replace `CDDrivesList.DrivesAvailable()`) or **cdparanoia/libcdio-paranoia** (but its jitter/error correction duplicates what CUERipper does in managed code, and it hides C2 detail CUERipper wants). sg_io on the raw `sr` node needs group `cdrom` permissions, not root, on typical distros.

## 4) Evidence of Linux use

- The official wiki (cue.tools/wiki/CUETools) states: users "have been able to use it under linux, using Mono, but in this scenario only WAV audio is supported" — a stale note predating the pure-C# codec ports (Flake/ALAC/TTA now target netstandard2.0); Wine with .NET Framework + VC++2008 runtime in a wineprefix is the documented route for the full GUI.
- Upstream intent is explicit in the tree: `CUETools.ARCUE` and `CUETools.Converter` target `netcoreapp2.0` (RuntimeFrameworkVersion 2.0.9, `CheckEolTargetFramework=false`), and README lists ".NET Framework 4.7 and .NET Core 2.0" as build requirements — i.e. `dotnet run`-able CLIs, though the wiki warns "CUETools.ARCUE.exe has far too many dependencies to use as a command line program outside of the CUETools suite."
- No Linux CI exists (only `CI-windows.yml`, `release-windows.yml`, `build_ffmpeg_dlls.yml`); a hydrogenaudio thread "CUEtools on linux?" (topic 118414) exists but returned HTTP 403 to automated fetch. Net: verification (ARCue) and conversion paths are Linux-feasible on dotnet with managed codecs; ripping is the one part with no Linux implementation at all.

Caveat: the GitHub tree API response was truncated mid-listing, so per-project data above comes from directly fetched csproj files; frameworks quoted are exact from those files at master (version stamps 2.2.6.0).
